# Передача задачи: Telegram-бот PODSLUSHANO ZIEIT

Этот документ предназначен для отдельного экземпляра ИИ-разработчика, который будет заниматься Telegram-ботом. Он описывает контекст платформы, ожидаемую интеграцию и данные, которые нужно запросить у владельца проекта. Документ не содержит секретов.

## Готовый промт для следующего экземпляра

```text
Ты работаешь над Telegram-интеграцией проекта PODSLUSHANO ZIEIT — социальной платформы студентов ЗИЭИТ. Сначала изучи этот файл целиком и текущее состояние репозитория. Не начинай с реализации всего проекта.

Согласованная архитектура:
- Next.js, React, TypeScript, Tailwind CSS, shadcn/ui.
- PostgreSQL в Supabase, Drizzle ORM; Supabase Storage для файлов.
- GitHub → Vercel для сайта. Не заменяй это на GitHub Pages или другую схему хостинга.
- Telegram-бот — отдельный интерфейс общей платформы, а не отдельная база пользователей.
- Регистрация пользователей происходит только через личный чат с ботом. На сайте остаётся только вход по логину и паролю; публичную регистрацию на сайте не добавлять.
- Пароли хешируются Argon2id на сервере. Нельзя писать пароль или секреты в логи, исходный код, GitHub, сообщения модераторам или ответы API.
- Данные сайта и бота хранятся в общей PostgreSQL. Telegram не является базой данных.
- Работай поэтапно, сохраняй существующее поведение, запускай релевантные проверки и объясняй обнаруженные несовместимости до изменения архитектуры.

Цели Telegram-интеграции:
1. Личный бот:
   - регистрация: предупреждение о передаче пароля в чат с ботом, при необходимости запрос контакта отдельной кнопкой Telegram, имя профиля, уникальный логин, пароль;
   - привязка существующего аккаунта, восстановление доступа и отвязка Telegram с дополнительным подтверждением;
   - справка, информация об аккаунте и будущие уведомления;
   - никогда не пересылать пароль или личные переписки в группу модерации.
2. Закрытая группа модерации:
   - публикации/жалобы, для которых действительно требуется модерация;
   - действия «Одобрить», «Отклонить», «Запросить исправление», «Подробнее»;
   - каждое решение проверяется backend по роли модератора, текущему статусу и допустимому переходу состояния;
   - конкурирующие решения должны атомарно разрешаться в базе данных и журналироваться;
   - анонимные публикации показываются только под именем «Аноним». Не раскрывать скрытого автора модераторам автоматически;
   - личные сообщения не пересылать в группу. Контекст личной переписки может быть доступен лишь в рамках конкретной жалобы и отдельной проверки полномочий.
3. Публичный канал:
   - публиковать только одобренные материалы, разрешённые автором для Telegram и публичные по правилам платформы;
   - анонимные материалы публиковать только как «Аноним»;
   - сохранять связь публикации сайта с сообщением канала и защищаться от дублей.

Требования к реализации:
- До написания кода уточни неизвестные настройки/решения у владельца; не придумывай токены, ID чатов, URL или команды.
- Используй Telegram Bot API через webhook; проверяй секрет webhook и аутентифицируй внутренние запросы к backend. Не доверяй данным от клиента или Telegram без проверки.
- Все разрешения, проверка ролей, валидация входных данных и изменение статусов выполняются на сервере.
- Пароли принимать только в личном чате с ботом; предупредить пользователя, что Telegram передаёт сообщение боту. Если возможно, удалить сообщение с паролем после обработки, не сохраняя его в логах/очередях. Не отображать пароль в ответе.
- Уникальность логина и Telegram ID обеспечить ограничениями PostgreSQL, а регистрацию выполнять транзакционно и идемпотентно.
- Секреты хранить только в переменных окружения/хранилище секретов Vercel и не просить владельца отправлять их в чат, issue или этот документ.
- Для надёжной отправки предусмотреть outbox/очередь, повторные попытки, идемпотентность, хранение Telegram message_id и безопасное журналирование ошибок без секретов.
- Учитывать локальный запуск и отдельные development/production настройки. Не отправлять тестовые события в production.
- Добавлять только функциональность текущего этапа; не делать декоративные кнопки, которые ничего не выполняют.

Сначала верни короткий план с точными файлами/эндпоинтами, схемой потока регистрации и списком неизвестных параметров. После согласования реализуй один ограниченный этап, добавь необходимые тесты, запусти проверки, а затем сообщи, что настроить вручную. Не публикуй секреты и не выполняй деплой без отдельного разрешения.
```

## Что передать следующему экземпляру

Передайте ему ссылку/доступ к репозиторию и этот файл: `docs/telegram-bot-handoff.md`. Уточните:

- Какой этап нужен первым: регистрация, webhook/привязка, модерация или публикация в канал.
- Username бота без токена и, если уже созданы, публичный username канала и назначение закрытой группы.
- Будут ли подтверждать телефон, и обязательно ли это для регистрации.
- Какие поля профиля обязательны; правила допустимых логинов и паролей.
- Какие роли имеют право модерировать и какие решения им доступны.
- Нужны ли публикации в канале сразу после одобрения или только для постов с отдельным согласием автора.
- Какие уведомления бот должен отправлять и как часто.
- Где будет локально запускаться бот и какой способ webhook/туннеля предпочтителен для разработки.
- Доступные тестовые аккаунты/чаты и ожидаемые сценарии проверки (без передачи настоящих паролей).

## Секреты и доступы — только локально

Не вставляйте в этот документ, чат с ИИ, GitHub issue/PR или исходный код:

- `TELEGRAM_BOT_TOKEN`;
- токены/секрет webhook;
- ключи внутреннего API;
- `DATABASE_URL`, пароль базы данных или ключ Supabase service role;
- реальные пароли пользователей.

Передавайте секреты только через локальный `.env.local`/`.env` (который исключён из Git) или защищённое хранилище проекта. При необходимости укажите имена переменных и сообщите, что они настроены, не раскрывая значения.
